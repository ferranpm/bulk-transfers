# 14. Error model

Status: Accepted (2026-09-28)

## Context

The contract only defines success, so the error shape is ours to design. Clients need one stable,
machine-readable format for every failure: validation errors, business rejections (insufficient funds, unknown
account, key reuse) and infrastructure errors. If each controller builds its own hashes, the format drifts and
status codes end up scattered across the code.

## Chosen

- A `DomainError` base class in `app/errors/`. Each subclass declares its contract in one line:
  `configure code: "insufficient_funds", http_status: :unprocessable_content, default_message: "Insufficient funds"`.
- Instances carry `code`, `http_status`, `message` and `details`, and `to_h` renders the single envelope:
  `{ "error": { "code": ..., "message": ..., "details": ... } }`.
- `Api::BaseController` renders any `DomainError` with its own status.

## Discarded (why)

- **Rails' default error pages / ad-hoc hashes per controller**: HTML error pages for a JSON API, and
  inconsistent shapes.

## Consequences

- Adding an error means adding a subclass. The status code and error code live next to each other.
- Error classes are unit-tested against the API contract table in the README.
