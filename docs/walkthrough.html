Backend banking challenge · submission walkthrough

Pay hundreds of salaries in one request. All of them, or none.

A Rails and PostgreSQL service that debits many credit transfers from one account atomically. It stays correct with several load-balanced instances, crashes at any point and clients that retry.

POST /transfers/bulk + Idempotency-Key

01 · What the brief asks for

Four constraints, four answers

The happy path is simple: check the funds, insert rows, update the balance. The brief's hints are what make it hard. Each one maps to a specific mechanism.

Ensure you don't lose a cent during processing

Integer cents everywhere. bigint columns, Integer in Ruby, amounts parsed from strings. JSON numbers are refused because a float has already lost the exact value.

Assume multiple load-balanced instances

PostgreSQL is the coordinator. One SELECT … FOR UPDATE on the account row serialises check-then-write across every instance. No in-process mutex, no Redis.

Any process can crash at any point, and networks glitch

One transaction plus an idempotency key. A crash before commit rolls back. A crash after commit is resolved by a retry with the same key, which gets the original result back.

Don't accept what the balance shouldn't allow, and vice versa

Three layers against overdraft: the check under the lock, a guarded UPDATE, and a CHECK (balance_cents >= 0) constraint. Refusals change nothing.

02 · The core problem

Two instances, one balance

Balance €100. Two bulks of €70 arrive at the same moment on different instances. Each would fit alone; together they don't. This read-check-write race is what the whole design is built around. The same race would let two retries of one request both debit.

Why a pessimistic row lock and not the alternatives

A conditional UPDATE … WHERE balance_cents >= total also prevents the double spend, but it doesn't serialise the idempotency lookup: two same-key retries would both try to debit and we'd rely on a unique-index exception to undo one. Optimistic locking causes retry storms on a hot payroll account. SERIALIZABLE needs a retry loop around every transaction. Advisory locks are a second scheme future code must remember. One row lock keeps every rule in plain Ruby, in one place. Different accounts never wait on each other, and a single lock can't deadlock.

03 · How a request flows

Cheap checks outside, one short transaction inside

Validation and fingerprinting happen before touching the database, so a malformed request never adds contention. Everything that depends on the balance or on previous requests happens under the lock.

04 · Contract as implemented

Five statuses, one error shape

The brief's prose says 201 while its OpenAPI block says 204. We chose 201 with a body listing every created transfer with its id, in request order, so a payroll client can match each line of its file to what the bank created. The only addition to the contract is the Idempotency-Key header.

Amounts are decimal strings in euros ("14.5", "61238"), positive, at most two decimals. Exponent forms like "2e3" are refused. Names are capped at 70 characters and descriptions at 140, matching SEPA field limits so every accepted transfer can later go out on SEPA rails.

05 · Operational scenarios

Crashes and retries

The server can't tell a second payroll from a retry of the first by looking at the body. The client says "same request" with the key; the server stores the key with the bulk, so it exists only if the bulk was applied. The fingerprint is computed over canonical JSON, so a retry with different whitespace or key order still counts as the same request.

ScenarioOutcome
Crash before COMMITPostgreSQL rolls everything back. The retry with the same key is processed as new.
Crash after COMMIT, before respondingApplied. The retry gets 200 with the original body; nothing paid twice.
Client disconnects mid-requestServer finishes normally. The retry gets 200 or the same refusal.
Connection lost during COMMITOutcome unknown to the server, so 503. The retry with the same key resolves it.
Two requests on one accountThe second waits on the lock, then sees the first one's committed result.
Lock held longer than 2 s503 with Retry-After: 1; nothing applied.
Several instances, or the database downInstances are stateless; all coordination is in PostgreSQL. If it's down, every request is a 503 and no money moves.
06 · What the tests prove

Eight invariants, tested against real PostgreSQL

No locks and no database calls are mocked. Concurrency specs run real threads on separate connections, released together so requests genuinely overlap. Every money-touching spec calls a shared expect_ledger_invariants! helper.

#Guarantee
1A balance is never negative.
2Balance = sum of the account's transactions.
3A bulk is applied completely or not at all.
4Each bulk's rows match its declared count and total.
5One key applies at most one bulk per account.
6Concurrent bulks never jointly exceed the balance.
7Every refusal (400, 422, 503) changes nothing.
8No floats on the money path; debits are negative, non-zero, EUR.

Three layers stop an overdraft

1

Funds check under the lock. Plain Ruby against the locked balance; raises InsufficientFundsError with both amounts.

2

Guarded UPDATE. WHERE balance_cents >= total; zero rows updated raises and rolls back.

3

Database constraint. CHECK (balance_cents >= 0), plus amount_cents <> 0, currency = 'EUR' and SEPA length limits.

Testing shape

  • Request specs are the largest layer: every status and error code, both samples.
  • Unit specs for branchy rules: amount parsing, Ledger, Result, fingerprint.
  • Operation specs assert result, balance and rows together.
  • Concurrency specs (:concurrency): two bulks that fit alone, exactly one accepted; parallel same-key requests, one bulk.

08 · How it was built

Claude Code as a pair, with guardrails first

The agent was treated like a new teammate: agree on the plan, set machine-checked conventions, review every step.

  1. step 1Understand

    Read the brief and name what makes it hard: several instances, crashes anywhere, client retries.

  2. step 2Plan before code

    A plan written together, questioned decision by decision: the setup, how work gets checked, the ordered steps.

  3. step 3Guardrails

    RSpec, RuboCop, Brakeman and bundler-audit behind one bin/ci, plus a committed CLAUDE.md.

  4. step 4Iterate

    Red/green TDD, one commit per step, pushing back when a result didn't fit.

  5. step 5Final review

    A pass over the whole history found two paths ending in a 500. Both fixed and covered by specs.

Conventions as code

Changing "how we write code here" means adding a cop, even a custom one. Agents were told to ask instead of silencing a rule; when one worked around a rule, review caught it and it became a recorded decision.

Pushed back on

The first 201 proposal was a bulk summary. It became every created transfer with its id, so a payroll client can reconcile line by line.

Caught in review

A NUL character in a counterparty name, and an unexpected unique-index violation. Both returned 500; both now have specs.

Issues faced

  • Strong parameters hide type errors. permit silently drops wrong types, so the client would see "missing". The controller whitelists keys itself.
  • Race specs that pass vacuously. Transactional fixtures hide each thread's writes. Concurrency specs commit for real and truncate afterwards.
  • Testing a 503 without mocks. A second connection holds the real lock, with a short lock_timeout.
  • Bulk writes versus the lint rule. insert_all! skips validations; kept with a justified inline exception, DB constraints as the safety net.

09 · Scope

Not built yet, on purpose

Left out deliberately rather than half-built.

  • Bulk size cap and async processing. A very large bulk holds the account lock longer (others get 503 after 2 s) and rolls back past the 10 s statement timeout. Fix: a cap, with larger bulks answered 202 and processed by a job.
  • Full IBAN/BIC validation. Shape only today; production should use ibandit (checksum, country lengths, BIC directory).
  • Idempotency key expiry (24–72 h TTL or time-partitioned tables).
  • Authentication and authorisation.
  • Executing the transfers on SEPA and publishing events downstream through an outbox.
  • Multi-currency.
  • A multi-instance Compose demo. Concurrency specs prove correctness across connections instead.
  • Metrics, tracing, rate limiting and a reconciliation job that alerts when balance ≠ sum of transactions.
Where it scales from here

One account's bulks run one at a time; different accounts run in parallel, so throughput grows with instances until PostgreSQL is the limit. Next steps: PgBouncer in transaction mode (no session state is kept), sharding by account since every transaction touches exactly one, and a per-account queue for very hot accounts. Structured log events (bulk_transfer.accepted / rejected / replayed / unavailable with duration_ms) are the base for metrics and alerting.
